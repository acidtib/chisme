thelast thingyou told me was Short answer: it's fundamentally an Apple/macOS limitation, which Bun inherits by default — but Bun gives a documented escape hatch, so it's solvable, not a dead end.

The precise picture:

- The root cause is Apple's system SQLite. macOS ships libsqlite3 compiled without loadable-extension support (Apple disables it). This bites any program that uses the system SQLite — Python's sqlite3, node-sqlite3, etc. all hit the same wall on macOS. It's a well-known macOS pain point, not specific to chisme.
- Bun's part is a default, not a hard limit. On macOS Bun links bun:sqlite against Apple's SQLite for a ~50% speed win, so it inherits "no extensions" by default. But Bun ships an override: Database.setCustomSQLite("/path/to/vanilla/libsqlite3.dylib") before opening any DB. Point it at an extension-capable SQLite and loadExtension works. On Linux/Windows Bun uses its own bundled SQLite, which is why those load sqlite-vec fine.

So it's not "Bun can't do this on macOS" — it's "Bun defaults to Apple's SQLite, and you must supply a vanilla one to load extensions." The fix is to bundle a vanilla libsqlite3.dylib (per arch) with the macOS binary and setCustomSQLite to it — exactly the pattern we already use for embedding vec0 and the WASM.

And to right-size the "blocker":
- Keyword search is unaffected on macOS — it's fully functional; FTS5 is built into Bun's SQLite and needs no extension.
- Only the semantic/vector layer (sqlite-vec) needs the loadable extension, so that's the only thing missing on macOS today.
- It's fixable with the custom-SQLite appg ~2 small dylibs, giving up Apple-SQLite's speed on macOS, and that I can only validate it via CI (I'm on Linux).

So: real and annoying for macOS semantic, you want me to go ahead and do thesetCustomSQLite + bundled-vanilla-SQLite fix (full hybrid on macOS too), or ship v0.2.0 now with macOS as keyword-only and tackle this as a follow-up?
